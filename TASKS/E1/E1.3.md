## Description

Matching, commute and privacy all start from the profile. The commute card needs the faculty and the class start time;
the match score needs budget and lifestyle; the Host and housemates must see only what the student agreed to show.
See [PRD FR1.3](../../docs/product/PRD.md#module-1-authentication-and-verified-profile) and the stage table in PRD section 5.

## Work needed

1. ⬜ **Four profile steps** after the first verified sign-in: faculty and year; timetable; budget and lifestyle; privacy.
   Uses `StepProgressView` and the shared components.
2. ⬜ **Timetable entry**: day, start, end, building. Stored exactly like that (PRD acceptance), in `users/{uid}/private/timetable`.
3. ⬜ **Budget** as a min and max in integer sen (`budgetMinSen`, `budgetMaxSen`); the screen shows ringgit.
4. ⬜ **Lifestyle tags and "I have a car"** (`lifestyleTags` public, `hasCar` private).
5. ⬜ **Privacy toggles** that take effect at once and are enforced by Security Rules, not only hidden in the UI.
   Draft toggles in the schema: show phone to Connections, show photo to the Household only.
6. ⬜ **Initials, not a photo, by default** (`initials` on the public `users` document).
7. ⬜ **Profile gate**: a verified account without a finished profile goes to profile setup, not to the shell (see E1.4).
8. ⬜ **A repository interface** like `AccountService` (`ProfileRepository` plus a Firebase implementation), so the screens and
   view models are tested with a fake.
9. ⬜ **Tests for saving and loading a profile**, and for each field check (budget min not above max, timetable end after start).

## Acceptance (how QA checks it)

- [ ] A new verified account sees profile setup first, and cannot reach the tabs until the required steps are done.
- [ ] Closing the app halfway and reopening continues the profile where it stopped.
- [ ] A timetable entry stores day, start, end and building; an end time before the start is rejected.
- [ ] Budget min above max is rejected with a message under the field.
- [ ] The public profile shows initials and faculty, never the name or the photo, before a Connection.
- [ ] Turning a privacy toggle off hides that detail from a second test account immediately (checked with two accounts).
- [ ] With the emulator rules loaded, reading another student's `private/profile` or `private/timetable` is denied.
- [ ] `./gradlew testDebugUnitTest` passes.

## Not in scope, and why

- **Editing the profile later.** That is E10.1 (P1). This story only creates it.
- **Profile photo upload.** The photo is off by default (initials); Firebase Storage is not used on the free plan; photos go to Cloudinary Free through an upload signed by the Worker (decided 31 Oct 2026, E2.1).
- **Compatibility questionnaire** (sleep, cleanliness, noise, cooking, smoking, pets, budget). That is E6.1 and writes to `matchProfiles`.
- **Real personal data in tests or examples.** Fictional names only (PDPA).

## Notes

### Decisions taken

- 30 Oct 2026, Ary: UM student email only, so the profile can rely on a verified student (see E1.1).
- Data shape proposed by Gathan in `docs/schema.md`: public `users/{uid}` (`initials`, `faculty`, `year`, `lifestyleTags`) and private
  documents `private/profile`, `private/timetable`, `private/photo`. Not agreed with Ary or Aaron yet.
- 31 Oct 2026, Ary: Gender: required at registration (profile setup right after sign-up), male or female, and shown on the profile so others see it. Rooms are not hidden automatically: the Rooms search and the housemate page have a filter chip the user picks (Male / Female / Any), default Any. PRD FR1.3 and section 8 updated.
- 31 Oct 2026, Ary: The gender field lives in the public `users/{uid}` document, because others must see it.
- 31 Oct 2026, Ary on Claude's recommendation: Sources: the faculty list is UM's official list of faculties and academies, kept in a string resource with its source link and date; the building list comes from the same place search as Listings (E2.1). Lifestyle tags come from the survey (T1); until 13 Nov use a short starter set and mark it as a draft.
- 31 Oct 2026, Ary on Claude's recommendation: Timetable day format: stored as ISO weekday numbers 1 to 7 (Monday = 1), matching `match.js`; `start` and `end` are `"HH:mm"` in Malaysia time, and the commute function uses `start` as the class start. Needs review by Gathan and Aaron.
- 31 Oct 2026, Ary on Claude's recommendation: A Host needs no extra profile data: any student can be a Host; unit details live in the listing, and the phone number stays in the private document until a Connection.
